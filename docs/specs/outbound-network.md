# 出口网卡选择与跳过代理设计

> 状态：功能已实现；跨平台与运行环境验证范围见文末。
> 基线：`main a83073a`。下文保留设计约束；实际行为和诊断范围见“实现说明”。
> 首期范围：逻辑渠道的出口策略、六类渠道请求、关联探测、Web 配置与诊断；支持 Linux 和 macOS 的网卡绑定。

## 目标与使用边界

为渠道增加两个独立控制：使用哪张出口网卡，以及是否使用 Yunqi 配置的应用层代理。用户可以保留已有代理地址，临时选择强制直连，也可以让某个渠道的请求通过指定网卡发送。

首期按逻辑渠道配置，同一逻辑渠道的多协议物理路由共享设置。未配置时维持现有行为。网卡选择属于该渠道的硬约束，绑定失败后终止此渠道尝试，不静默改走默认网卡；强制直连不因连接失败、403 或 451 自动使用代理。

这里的“跳过代理”指不使用 HTTP、HTTPS、SOCKS 应用层代理。操作系统路由、VPN、TUN、透明转发及出口 NAT 仍可影响最终路径，不能承诺任意 VPN 环境都能通过此功能绕过。产品提示应写“跳过 Yunqi 应用层代理”，不能仅凭绑定成功就显示“已绕过 VPN”。

自动故障转移或竞速选择其他渠道时，各渠道仍遵循自己的出口配置。若要求整次请求固定出口，应显式选择一个渠道，或让所有可选渠道使用相同出口策略。现有 `X-Channel` 显式选择会限制渠道选择并关闭竞速；本期不增加允许代理调用方任意指定服务器网卡的请求头。

## 当前实现与接入点

- `backend-go/internal/httpclient/client.go` 统一管理普通、流式和直连优先客户端，缓存键包含超时、TLS、代理地址等条件，目前没有网卡或 DNS 策略。
- 渠道的 `proxyUrl`、`proxyPreferDirect` 保存在 `UpstreamConfig` 和 `LogicalChannelSettings`，通过共享字段与逻辑渠道 CRUD 同步；新增字段应沿用这套数据路径。
- `direct_first.go` 在直连网络错误、403、451 且请求体可重放时回退代理。这与“强制直连”是两种行为。
- 当前自建 `http.Transport` 没有设置 `ProxyFromEnvironment`。空代理地址的这条客户端路径已经不读取 `HTTP_PROXY`、`HTTPS_PROXY`，不能把这次功能描述为修复该路径的环境代理继承。其他独立客户端需要逐一检查。
- `metadata_guard.go` 同时提供连接地址检查和代理请求的域名预检查；新增 Dialer、Resolver 和代理处理必须保留这些检查。
- 普通代理发送入口为 `handlers/common/request.go`；ping、能力测试、渠道发现、保活、余额探测也有客户端构造入口，不能只改实际推理请求。

Go 对 `Transport.Proxy` 的约定是 nil 时不使用代理，见 [Transport 文档](https://pkg.go.dev/net/http#Transport)。本设计要求显式构造策略对应的 Transport，不通过修改进程环境变量改变代理行为。

## 配置与兼容规则

在 `LogicalChannelSettings` 增加可选的 `outboundNetwork` 对象，并同步到六类 `UpstreamConfig` 的运行时投影。对象缺失等同于 `proxyMode=legacy`、不指定网卡、使用系统 DNS。

逻辑渠道 settings 配置示例：

```json
{
  "proxyUrl": "http://127.0.0.1:7890",
  "proxyPreferDirect": true,
  "outboundNetwork": {
    "proxyMode": "direct",
    "interfaceName": "en0",
    "addressFamily": "ipv4",
    "dns": {
      "mode": "bound",
      "servers": ["192.0.2.53:53"]
    }
  }
}
```

`192.0.2.53` 是文档示例地址，使用时须替换为实际可达的 DNS 服务器。示例中的代理地址被保留，但在 `direct` 模式下不参与请求。

### 代理模式

- `legacy`：沿用已有 `proxyUrl` 和 `proxyPreferDirect`。有效代理地址为空时直连；配置代理且开启直连优先时保留原有回退规则。
- `direct`：强制不使用应用层代理，忽略保留的代理地址和直连优先开关；不回退代理。
- `proxy`：必须使用现有 `proxyUrl`，地址缺失或无效时报告配置错误，不转为直连。
- `direct_first`：先直连，按现有条件回退配置代理；必须具备有效代理地址，并保留请求体可重放、取消和响应提交边界。

新对象不重复保存代理 URL，也不反向改写旧的布尔字段。显式模式优先于旧字段，回到 `legacy` 才重新读取旧设置，避免两个配置源相互覆盖。既有合法配置保持原行为，新模式拒绝缺失、格式错误和不支持的代理协议。

### 网卡与地址族

`interfaceName` 为空表示由操作系统选择路由；非空表示严格绑定该接口。持久化接口名称，不持久化容易重用的 ifindex；运行时重新解析名称、索引、地址和状态。

`addressFamily` 接受 `auto`、`ipv4`、`ipv6`，默认 `auto`。自动模式保留双栈连接能力，但两个地址族的 socket 都必须满足同一接口约束。单栈模式不偷偷切换到另一个地址族。

接口消失、关闭或地址族不匹配时保留已保存设置并报告不可用，不清空字段。正式配置加载不能因为一张网卡暂时离线就阻止整个网关启动。

### DNS

不绑定网卡时默认 `dns.mode=system`。显式绑定网卡时首期要求 `dns.mode=bound` 并填写 DNS 服务器，避免 TCP 走指定网卡、域名解析却继续走本地代理的情况。

`servers` 只接受带端口的 IP 字面量，IPv6 使用 `[地址]:端口`；首期支持常规 UDP DNS 及需要时的 TCP 回退。DNS 服务器本身也通过同一接口连接，不能因解析失败回退系统 Resolver。链路本地 IPv6 的 zone 必须与所选接口一致。

HTTP CONNECT 或 SOCKS 的目标域名可能由代理端解析。`bound` 约束的是 Yunqi 发出的 DNS 查询，不控制代理端的解析网络；代理请求的元数据域名预检查也必须使用该 Resolver，而非另走 `net.DefaultResolver`，其拒绝与放行规则保持现有安全语义。

### 配置读写与迁移

新增 `OutboundNetworkConfig` 及更新 DTO；PATCH 必须区分“不修改”、显式清除对象和更新对象，不能用空字符串或 false 的 truthy 判断实现清除。

逻辑渠道创建、编辑、复制、导入导出、共享字段同步、Channels V3 投影和托管渠道重建都须保留该对象。旧配置无需批量落盘迁移。旧字段继续被读取，但不允许把新模式同时编码成两套独立状态。

新建或更新时校验枚举、代理组合、接口名格式、DNS 地址和数量上限；建议 DNS 最多 4 个。动态网卡状态作为可用性信息返回，保存配置本身不自动发送上游请求。异机导入后不存在的接口应显示不可用，不自动替换为本机默认接口。

## 传输层设计

建议在 `ClientOptions` 增加可选的 `OutboundNetwork`，由无网络副作用的 `ResolveOutboundPlan` 把设置与兼容字段解析成不可变的运行时计划。普通、SSE、临时测试客户端和关联任务统一消费计划。

所有具备渠道上下文的旧 `GetStandardClient` 等调用必须迁移到显式传递网络设置的 `GetClient` 或 `NewClient`。旧签名只保留给不归属渠道的兼容请求，不能凭代理 URL 反查渠道。底层收敛到统一 factory，避免新旧方法相互调用形成递归。

一次物理路由尝试冻结自己的计划和版本，Key 轮换不改变出口。配置变化或故障转移选择其他物理路由时重新解析，并记录实际采用的策略。

出站连接按以下顺序构造：

1. 校验配置并解析接口快照，得到代理模式、网卡、地址族、DNS 和策略指纹。
2. 创建保留现有元数据地址检查的 Dialer，组合 socket 绑定操作。
3. 按需创建专用 Resolver；DNS Dialer 不再次使用自身 Resolver，避免递归解析。
4. 为直连或代理分支构造新的 Transport，明确设置 `Proxy` 和 `DialContext`。
5. 用完整策略键获取或创建连接池，执行请求及重定向检查。
6. 记录实际分支和本地连接地址；取消、竞速提交权和失败分类继续使用现有请求上下文。

### 平台绑定

Linux 使用按平台编译的 socket 绑定实现，首选 `SO_BINDTODEVICE`；macOS 分别使用 IPv4 的 `IP_BOUND_IF` 和 IPv6 的 `IPV6_BOUND_IF`。选项通过 `golang.org/x/sys/unix` 常量访问，不在通用代码中硬编码数字。

绑定能力需在目标内核、权限和网络命名空间内验证。权限不足时返回可识别错误，不自动更改 capabilities、启用 privileged 容器、重写路由表或关闭 VPN。

仅设置 `net.Dialer.LocalAddr` 表达的是源地址选择，本设计不把它视为实现严格网卡约束的充分条件。其他平台保持无绑定路径兼容；显式指定接口时返回不支持，不伪装成功。

对应接口定义见 [Linux socket](https://man7.org/linux/man-pages/man7/socket.7.html)、[Apple IPv4 头文件](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet/in.h)、[Apple IPv6 头文件](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet6/in6.h) 和 [Go Dialer](https://pkg.go.dev/net#Dialer)。

### 代理连接与 DNS

HTTP/HTTPS 代理模式绑定的是 Yunqi 到代理服务器的连接，代理服务器到上游的出口由代理程序控制。本地代理位于 loopback，而所选接口是物理网卡时可能不可达；诊断应明确指出该连接目标，不能为使测试通过而自动解绑接口。

SOCKS 构造器须将绑定后的基础 Dialer 作为转发 Dialer，替换当前 `proxy.Direct`，并保留 `ContextDialer` 的取消能力。强制直连必须使用独立 Transport，不能复用此前已安装 SOCKS DialContext 的实例。

直连优先的两个分支都遵守同一网卡和本地 DNS 约束。绑定错误、策略不支持、父请求取消、竞速败出及元数据目标拒绝属于终止错误，不进入代理回退；403/451 与可重放网络故障仍遵循显式选择的 `direct_first` 语义。已经开始交付的 SSE 不切换出口重放。

专用 DNS 使用 `net.Resolver{PreferGo: true, Dial: ...}`，处理 UDP/TCP、A/AAAA、取消及总时间预算，不修改全局 Resolver 或 `GODEBUG`。具体能力见 [Go Resolver](https://pkg.go.dev/net#Resolver)。

### 连接池与热更新

缓存键至少包含流式标记、超时、TLS 策略、有效代理模式、代理身份指纹、接口名与运行时索引、地址族、DNS 配置、配置版本及接口代际信息。代理凭证不写入日志，指纹使用规范化配置的摘要。

策略变化后，新请求使用新池；旧池只关闭空闲连接，存量请求和 SSE 自然完成，不统一取消在飞请求。缓存需有数量或存活期上限，避免频繁修改 DNS、代理和接口产生无界旧池。

网卡名称或索引变化后重新校验，新连接不能复用旧接口代际的池。真实网卡掉线本身可能使已有连接失败，应用不能承诺此类物理变化下流不中断。

## 请求覆盖与故障转移

首期验收须覆盖六类渠道的普通、流式、multipart 请求，以及 Responses 的 WebSocket 入口所触发的上游请求。若调用链存在独立 WebSocket Dialer，也要复用相同的网络计划，不能仅覆盖普通 HTTP 后就宣称全路径支持。

同渠道的 `/models` 查询、能力测试、配置发现、URL 预热、L1/L2 保活、余额探测及渠道关联的资源下载都传递相同策略。表单尚未保存时的临时测试通过 DTO 传入完整网络设置，测试不得改动正式配置。

账号登录、订阅同步、汇率或基准数据更新等无法唯一归属渠道的流量不从任意渠道推断设置。账户级或实例级默认出口列为后续扩展；首期界面明确“仅本逻辑渠道及其关联请求生效”。

增加可通过 `errors.As` 识别的本地出口错误，包括接口不可用、不支持绑定、权限不足、地址族不匹配、本地 DNS 配置无效及绑定 DNS 不可达。这类错误停止同渠道 Key 轮换，不拉黑 Key、不标记 URL 失败、不计模型熔断或自动权重失败，也不从 403/451 分类分支误判。

外层可以按现有物理 Route 选择其他渠道，各次尝试都携带各自的策略指纹；需要固定整个逻辑请求出口时使用前述显式渠道约束。竞速每个分支独立取得客户端，赢家结算保留实际出口信息，败出取消仍按 `ErrRacingSuperseded` 处理。

绑定成功后的常规上游连接错误仍按既有失败分类处理；本地错误分类不能仅凭 `net.Error` 接口判断。

所有可选路由均因本地出口不可用而被拒绝时，返回可识别的 503 `network_egress_unavailable`；管理写入中的格式错误返回 400。不把本地权限或网卡问题显示为上游鉴权失败。

## Web 界面与管理 API

在逻辑渠道编辑器的传输设置中增加“代理路径”“出口网卡”“地址族”和“DNS”控件。代理路径选项为“沿用现有设置”“强制直连”“使用代理”“直连优先”，强制直连时保留代理地址但禁用其执行相关控件。

出口网卡默认“系统路由”；列表展示接口名称、IP、运行状态和是否为 loopback/隧道。禁止用客户端浏览器看到的网卡替代服务端接口。不可用的已配置接口仍保留在列表中并显示原因。

管理员接口：

- `GET /api/network/interfaces`：只枚举当前服务进程可见的接口、地址和平台绑定能力，不拨号或抓包；与现有管理路由使用相同管理员鉴权。
- `POST /api/network/diagnose`：显式操作时验证临时网络计划，返回配置、DNS、TCP、TLS 各阶段结果，不保存渠道设置。

诊断只接受已有渠道 UID 及其 BaseURL，或受与现有配置测试同等校验的临时 BaseURL；限制为 HTTP/HTTPS，保留重定向和元数据目标保护。默认检查 DNS、TCP、TLS，不携带 API Key、不调用计费推理接口，也不访问额外的公网 IP 查询站点。

返回 `interfaceName`、`interfaceIndex`、`bindingApplied`、实际 `localAddress`、连接 `remoteAddress`、有效代理分支与失败阶段。socket 绑定成功和本地 IP 都不能单独证明 VPN 已被绕过；界面只展示实际可观测的结果。

路由预演展示出口计划但不拨号。日志记录策略来源、指纹、代理分支、绑定结果和本地错误类别，代理 URL 按现有方法脱敏。

## 部署边界

容器只能选择自身网络命名空间内可见的接口。Docker 中的 `eth0` 不是宿主机物理网卡的别名，容器出口仍可能经过宿主机 NAT 或 VPN；参见 [Docker 网络说明](https://docs.docker.com/engine/network/)。诊断界面应显示运行环境和可见接口，不能在容器里列出宿主机的 `en0` 后承诺绑定成功。

本功能不自动修改 Docker 网络模式、系统代理、VPN 路由或防火墙。需要宿主机策略路由或代理软件出站规则的部署，由运维单独配置。Windows 等未实现绑定的平台仍可使用原有代理和直连路径。

## 实施顺序与验收

1. 增加配置类型、兼容解析、逻辑渠道与六类投影同步，完成只读接口枚举和平台能力检测。
2. 实现 Linux/macOS 绑定、专用 Resolver、HTTP/SOCKS 适配及连接池隔离；底层收敛到统一 factory，迁移全部渠道关联的旧客户端调用。
3. 贯通实际代理、发现、能力测试、预热、保活、余额及临时测试，再接入 Web 编辑和分阶段诊断。
4. 完成平台集成和端到端验收后开放功能。全局默认、账户级出口和策略路由自动化另行设计，不隐含在首期承诺中。

回归场景至少包括：

- 缺失新字段时普通/SSE 客户端保持原行为；四种代理模式及非法组合有明确结果。
- 配置了有凭证代理后选择 `direct`，请求与重定向均不触发 HTTP 或 SOCKS 代理；回到 `legacy` 可恢复原设置。
- 两张测试接口之间切换时连接池不串用；接口下线、重命名、索引重用及 IPv4/IPv6 不匹配都不回落默认网卡。
- DNS 的 UDP、TCP、A、AAAA 与取消使用所选接口；解析失败不改走系统 DNS，元数据检查也不另发查询。
- HTTP CONNECT、HTTPS 代理、SOCKS、直连优先分别覆盖接口约束、取消、不可重放请求和已提交 SSE。
- 普通、multipart、流式、WebSocket 入口及关联探测使用相同计划；逻辑渠道编辑和托管重建不丢字段。
- 本地出口错误不会轮换同渠道 Key、污染熔断或把竞速败者当赢家；跨渠道尝试展示实际策略变化。
- 管理接口拒绝仅有代理权限的调用；临时诊断不写配置、不携带 Key、不触发计费调用。
- 热更新不取消在飞 SSE；新请求立即使用新策略，空闲旧池可回收且缓存规模有界。
- Linux/macOS 的真实绑定与 DNS 抓包验收在专用测试环境完成；权限不足、不支持平台及 Docker 网络命名空间均有明确结果。

单元测试使用可注入的接口枚举、socket 绑定与 DNS Dialer；绑定正确性的集成测试在临时 network namespace、专用虚拟机或测试机上进行，不在运行服务的宿主机上修改路由、切换网卡、停 VPN 或执行抓包。

## 实现说明

管理界面的标准添加、自定义快速添加和渠道编辑器提供代理模式、服务端网卡、地址族和 DNS 设置。点击“刷新网卡列表”只枚举服务端接口；不可用的已保存接口不会被清空。指定网卡时必须提供 bound DNS，保存接口不存在的配置是允许的，实际请求会报告本地出口不可用。

配置读取、共享投影、Channels V3、深拷贝及部分更新均保留 `outboundNetwork`；省略字段不修改，显式 `null` 清除策略并回到原有行为。强制直连保留 `proxyUrl` 和 `proxyPreferDirect`，执行时忽略两者。

普通、流式、multipart 和 WebSocket 入口的上游 HTTP 请求通过相同客户端路径；模型清单、能力/协议发现、ping、保活、余额、恢复探测、Copilot 渠道 token/catalog 请求和图片下载均传递渠道策略。账号登录、订阅同步等账户级请求仍使用原有账户设置。当前 URL warmup 模块仅依据请求结果排序，不主动发网络请求。

指定策略的客户端使用独立 factory，缓存按完整配置摘要、接口名称/索引/地址快照、超时及 TLS 参数隔离，上限 256。接口快照改变后旧客户端拒绝新的请求，下次取得客户端时生成新池；淘汰只关闭空闲连接，现存 SSE 不被主动取消。未设置策略的兼容客户端沿用旧构造路径。

绑定 DNS 查询失败属于本地出口错误，不能因为代理支持远端解析就忽略此错误。代理的 DNS 预检查使用专用 Resolver，元数据地址检查仍作用于实际连接和每次请求/重定向。

`GET /api/network/interfaces` 与 `POST /api/network/diagnose` 均要求管理员权限。诊断接受临时配置或逻辑渠道 UID（`channelUid`），对实际直连目标或代理服务器检查 DNS、TCP、必要时的 TLS；直连优先分别报告两条路径。它不发送 HTTP 请求、不做 CONNECT/SOCKS 业务握手、不证明代理到上游可达、不验证 API Key。界面明确展示此范围。

请求日志可记录策略指纹和实际 socket 的本地/远端地址；路由预演返回所选渠道的出口设置，不拨号。接口清单中的绑定支持表示平台实现可用，不代表进程已经获得绑定权限，权限需通过显式诊断或实际请求验证。

### 验证边界

自动回归覆盖代理模式、强制直连及重定向、HTTP/SOCKS 基础 Dialer、DNS UDP/TCP、取消、元数据保护、池隔离与上限、配置设置/省略/清除、六协议共享和临时模型查询、管理员鉴权、无 HTTP 副作用诊断、本地出口失败不选择/惩罚 Key。macOS 使用临时 loopback 服务验证真实 socket 绑定；Linux 进行交叉编译检查。

两张物理网卡、VPN/TUN、不同 Linux 内核权限、容器网络命名空间及接口热插拔需要在专用环境进一步验收；不能把本机 loopback 测试或交叉编译当作这些环境的实测。此次实现和验证不更改宿主机路由、网卡、VPN、运行配置或现有服务进程。
